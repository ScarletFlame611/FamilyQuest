# Квест 6. Репозиторий прототипа FamilyQuest

Участники, работавшие очно: Суслова Анастасия, Урясьева Ксения

## Какое действие разбираем

Мы выбрали главный сценарий нашего прототипа: ребёнок отмечает домашнее дело выполненным, взрослый его подтверждает, и после этого на балансе ребёнка появляются звёздочки.

Для показа используем демо-семью, которую создаёт скрипт `python -m app.seed`. Имена, названия дел, стоимость и количество звёздочек ниже приведены для примера: это данные демо-семьи, и сценарий работает так же с любым другим делом и любой суммой. Например, у дочери Маши есть дело «Покормить кота» стоимостью 5 баллов. До подтверждения у неё 35 звёздочек, после подтверждения должно стать 40. Одновременно общая семейная цель «Поход с палатками» вырастает с 260 до 265 баллов из 300.

Сценарий уже можно пройти от начала до конца: данные проходят через настоящий API и сохраняются в PostgreSQL, без заглушек. При этом продукт ещё на стадии разработки, поэтому в нём возможны ошибки, которые мы пока не нашли, и часть поведения может измениться по итогам тестирования с детьми.

## Как действие проходит по коду

### Ребёнок отмечает дело

Детский режим целиком живёт в `frontend/src/child/`. Файл `ChildApp.tsx` смотрит на адрес страницы и, если это `/kid/task/<id>`, показывает экран дела из `screens/TaskScreen.tsx`. Этот экран загружает дело с сервера и, пока оно назначено ребёнку и ещё не отмечено, показывает кнопку «✓ Сделал!».

Когда ребёнок нажимает кнопку, экран вызывает функцию `mark` из `frontend/src/shared/api/endpoints.ts`. Она отправляет запрос `POST /api/tasks/{id}/mark`. Сам запрос собирает `shared/api/client.ts`: он подставляет детский токен в заголовок `Authorization` и добавляет заголовок `Idempotency-Key`. Ключ создаётся один раз на нажатие (`shared/lib/useAction.ts`), поэтому если связь оборвётся и запрос уйдёт повторно, сервер узнает его и не выполнит действие дважды. В режиме разработки запросы к `/api` перенаправляет на бэкенд Vite (`frontend/vite.config.ts`), на стенде это делает nginx (`frontend/nginx.conf`).

На бэкенде запрос попадает в роутер задач `backend/app/modules/tasks/api.py`. Перед этим `backend/app/deps.py` расшифровывает токен и узнаёт из него, кто делает запрос и из какой он семьи. Для ребёнка там же проверяется, что детская сессия ещё не завершена. Семья всегда берётся только из токена, поэтому подставить чужое дело в адрес не получится: сервер ответит, что задача не найдена.

Роутер передаёт действие в `backend/app/core/idempotency.py`. Если такой ключ уже приходил, клиент получает сохранённый ответ. Если нет, вызывается функция `mark` из `backend/app/modules/tasks/service.py`. Она блокирует строку задачи в базе, проверяет, что дело принадлежит именно этому ребёнку и находится в статусе «назначено», и переводит его в статус «отмечено». Если статус другой, например дело уже отмечено, сервер отвечает ошибкой 409. В конце роутер записывает событие в журнал детской сессии, который мы используем при тестировании интерфейса с детьми.

После успешного ответа ребёнок видит экран поздравления, а в карточке дела появляется надпись «⏳ Проверяют».

### Взрослый подтверждает

Взрослый возвращается в свой режим по PIN-коду и попадает на экран «Проверка» (`frontend/src/adult/HomeScreen.tsx`). Этот экран запрашивает у сервера все дела детей, которые ждут подтверждения. Каждое дело показано карточкой из `frontend/src/shared/ui/TaskCard.tsx`, и кнопка на ней отправляет запрос `POST /api/tasks/{id}/confirm`.

Подтверждать дела может только взрослый. Это проверяет сервер в `deps.py`, а не интерфейс: если отправить такой запрос с детским токеном вручную, он получит ошибку 403.

Функция `confirm` в `tasks/service.py` снова блокирует задачу, переводит её в статус «подтверждено» и вызывает `accrue` из `backend/app/modules/ledger/service.py`. Модуль `ledger` отвечает за баллы. Он блокирует счёт ребёнка, добавляет в журнал строку о начислении 5 баллов и увеличивает сохранённый баланс. В базе есть уникальный индекс, который не позволит записать второе начисление за то же дело, даже если повторный запрос как-то обойдёт ключ идемпотентности.

Изменение статуса задачи, запись в журнал и новый баланс сохраняются одной транзакцией. Либо применяются все три изменения, либо ни одного.

### Ребёнок видит результат

Когда ребёнок снова получает телефон, `ChildApp.tsx` при каждом переходе между экранами заново запрашивает баланс по адресу `/api/balance` (его отдаёт `backend/app/modules/ledger/api.py`). На экране появляется 40 звёздочек, а дело переходит в раздел «Сделано».

Прогресс общей цели отдельно не хранится. Функция `get_active_goal` в `backend/app/modules/goals/service.py` каждый раз считает его по журналу как сумму всех начислений семьи с момента создания цели, поэтому новые 5 баллов сразу попадают и туда.

## Как запустить и проверить самостоятельно

Сначала нужно поднять окружение и создать демо-семью. В файле `.env` (его можно скопировать из `.env.example`) задаются пароли базы данных и демо-пользователей.

```bash
cp .env.example .env
docker compose up -d
docker compose run --rm backend alembic upgrade head
docker compose run --rm backend python -m app.seed
```

Дальше описан проход на примере демо-данных. Если вы уже пользовались стендом или выберете другое дело, начальный баланс и названия будут другими, но баланс всё равно должен вырасти ровно на стоимость подтверждённого дела.

Откройте http://localhost:5173 и войдите как `mama@familyquest.local`. На главном экране нажмите «Включить детский режим» и выберите Машу: у неё 35 звёздочек. Во вкладке «Мои дела» откройте «Покормить кота» и нажмите «Сделал!». Потом выйдите из детского режима по PIN-коду `2580`, найдите это дело на экране «Проверка» и подтвердите его. Если снова включить детский режим для Маши, на балансе будет 40.

Запросы и ответы удобно смотреть во вкладке Network инструментов разработчика. В ответе на отметку статус дела `marked`, в ответе на подтверждение `confirmed`. Запись о начислении можно найти прямо в базе:

```bash
docker compose exec db psql -U $POSTGRES_USER -d $POSTGRES_DB -c \
  "select t.title, t.status, e.kind, e.amount from tasks t join ledger_entries e on e.task_id = t.id where t.title = 'Покормить кота' and t.status = 'confirmed' order by e.created_at desc limit 1;"
```

Тот же сценарий проверяется автоматически. Первый тест проходит весь путь через API, второй отправляет 50 одновременных подтверждений и убеждается, что баллы начислены ровно один раз:

```bash
docker compose exec backend pytest tests/test_ledger.py -k "critical_path or fifty_parallel"
```

## Почему мы так сделали

### Баллы меняются только через журнал

Начисление звёздочек — самая чувствительная часть сценария. Двое родителей могут подтвердить одно и то же дело одновременно, а связь на телефоне может пропасть посреди запроса. Нам важно, чтобы баллы начислялись ровно один раз, а баланс всегда можно было объяснить историей операций.

Поэтому изменять баллы может только модуль `ledger` (`backend/app/modules/ledger/`). Каждое начисление или списание добавляется в журнал отдельной строкой, а баланс на счёте служит только кэшем и обновляется в той же транзакции. От повторов защищают ключи идемпотентности (`backend/app/core/idempotency.py`) и уникальный индекс в `ledger/models.py`. Это проверяют тесты в `backend/tests/test_ledger.py`.

Сначала мы рассматривали более простой вариант, при котором баланс хранится одним числом в профиле ребёнка и модуль задач сам прибавляет к нему баллы. Но тогда невозможно понять, откуда взялось число на счёте, отмену пришлось бы делать правкой истории, а одновременные запросы приводили бы к двойным начислениям. Журнал добавляет всего одну таблицу. Зато после нагрузочного теста сумма журнала совпала с балансом на всех счетах.

### Детский режим работает по отдельному токену, а не через скрытые кнопки

В нашем сценарии ребёнок и взрослый пользуются одним телефоном. Родитель включает детский режим и отдаёт телефон ребёнку, а потом забирает его обратно, чтобы подтвердить дело. Ребёнок не должен иметь возможности подтвердить дело сам, даже случайно или если найдёт способ отправить запрос в обход интерфейса.

Поэтому при включении детского режима сервер выдаёт отдельный токен с ролью «ребёнок» и создаёт запись о детской сессии в базе. Это делает модуль `backend/app/modules/child_mode/`. Фронтенд в этот момент удаляет токены взрослого из памяти и хранилища браузера (функция `startChildMode` в `frontend/src/shared/api/endpoints.ts`), так что на телефоне остаётся только детский токен. Вернуть права взрослого можно только по ответу сервера на правильный PIN. Каждый запрос проверяется в `backend/app/deps.py`: с детским токеном можно отметить своё дело, но подтверждение и другие действия взрослого сервер отклоняет с ошибкой 403. Даже если ребёнок перезагрузит страницу или нажмёт «назад», `frontend/src/App.tsx` вернёт его в детский режим, потому что решение принимается по роли в сессии, а не по адресу страницы.

Самым простым вариантом было бы оставить на телефоне вход взрослого и просто прятать в детском режиме лишние кнопки. Но такая защита держится только на интерфейсе: достаточно открыть нужный адрес вручную, и ребёнок получит все права взрослого. Мы также думали о том, чтобы завести детям собственные аккаунты с паролем, но детям 6–7 лет сложно его вводить, и у многих нет своего телефона. Отдельный детский токен и сессия в базе дают настоящую проверку прав на сервере и при этом позволяют завершить детскую сессию с сервера, даже если запущено несколько экземпляров API. Эти проверки покрыты тестами в `backend/tests/test_child_mode.py` и `backend/tests/test_risks.py`.

### Один сервер, разделённый на модули, и отдельный фронтенд

Наш сценарий затрагивает сразу несколько частей системы: задачи, баллы, детский режим и общую цель. Если всё это работает в одном приложении с одной базой, подтверждение дела укладывается в одну обычную транзакцию, и не нужны ни очереди, ни согласование между сервисами.

Бэкенд написан на FastAPI и разделён на модули в `backend/app/modules/`. Внутри каждого модуля одинаковые файлы: модели, схемы, логика и роутер. Модули обращаются друг к другу только через функции из `service.py`, а все роутеры подключаются в `backend/app/main.py`. Фронтенд на React и Vite лежит отдельно в `frontend/`, а типы для запросов к API генерируются из описания бэкенда в `frontend/src/shared/api/schema.d.ts`. Как запускаются база, сервер и фронтенд, описано в `docker-compose.yml`.

Мы думали о том, чтобы вынести задачи и баллы в отдельные сервисы, но для прототипа небольшой команды это слишком много инфраструктуры, и подтверждение перестало бы быть одной транзакцией. Вариант с серверными шаблонами, например на Django, плохо подходит для детского режима: ребёнку нужен интерфейс, который сразу отзывается на нажатия и не перезагружает страницу. Благодаря чётким границам модулей мы сможем позже вынести работу с баллами в отдельный сервис, если это понадобится.

## Что пока не сделано

Сценарий проходит от начала до конца, но кое-что упрощено. Взрослый не получает уведомлений о новых отметках и сам заходит на экран «Проверка»: уведомления в прототип не входят. Ребёнок видит новый баланс только при переходе на другой экран, потому что `ChildApp.tsx` запрашивает его при смене страницы, а не получает обновления от сервера сам.
