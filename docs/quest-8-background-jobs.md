# Квест 8. Воркеры, очереди и восстановление после сбоя

Проект: FamilyQuest, веб-сервис, в котором домашние дела семьи становятся задачами с ценой в баллах.

Дата: 21 ноября 2026 года.

Команда (кто присутствовал на паре): Суслова Анастасия, Урясьева Ксения.

## Зачем это проекту

До этого квеста все действия в FamilyQuest выполнялись прямо в запросе: нажал кнопку, сервер сделал работу и ответил. Для подтверждения дела или покупки награды так и должно быть. Но в плане MVP есть действия, которые так делать нельзя: восстановление пароля по почте, ежедневная сверка баланса с журналом баллов, а для семьи ещё и выгрузка всех её данных. Такие действия занимают время, могут упереться во внешний сервис и не должны держать открытым запрос пользователя. На схеме C4 второго уровня для них давно нарисован отдельный контейнер «Фоновый обработчик», который читает очередь из PostgreSQL. В этом квесте мы его построили.

Мы сразу делали обработчик так, чтобы потом не переделывать. Очередь заданий получилась общей: модуль `jobs` ничего не знает о выгрузках, он умеет поставить задание, выдать его одному воркеру, принять результат и вернуть задание в очередь после ошибки. Письма и сверка в MVP станут просто новыми видами заданий в этой же очереди.

Первым видом задания стала выгрузка всех данных семьи. Это первая половина истории US-48 из полосы MVP: семья должна иметь возможность забрать свои данные, прежде чем удалить аккаунт. Она же закрывает часть юридического риска из нашего реестра: мы храним данные детей и обязаны отдавать их родителям по запросу.

## 1. Сценарий

Выгрузку запускает взрослый член семьи. В разделе «Ещё» он открывает экран «Данные семьи» и нажимает «Подготовить архив». Результат не нужен ему в ту же секунду, поэтому работу можно выполнить позже: собрать архив значит пройти по всем делам, всей истории баллов каждого участника, наградам, покупкам, целям и журналу детского режима. У семьи, которая пользуется сервисом год, это заметный объём, и держать ради него запрос открытым нельзя.

Пользователь получает ZIP-архив, в котором каждый раздел лежит отдельным файлом CSV для Excel: участники, дела, история баллов, награды, покупки, цели и журнал детского режима, плюс короткое пояснение. Паролей, PIN-кода и ключей входа в архиве нет. Готовый файл хранится 7 дней, потом воркер его удаляет.

Статус взрослый видит на том же экране. Сразу после нажатия выгрузка показана как «В очереди», когда воркер её забрал, как «Собираем архив», а если первая попытка сорвалась, как «Собираем, попытка 2 из 3». Готовая выгрузка показывает размер файла, срок хранения и кнопку «Скачать». Пока архив готовится, экран сам обновляет список раз в две секунды. Если все три попытки не удались, выгрузка показывается с текстом «Не удалось собрать выгрузку. Попробуйте ещё раз», а оператор видит последнюю ошибку в поле `last_error` задания.

Каждое задание отслеживается по идентификатору `job_id`. Отдельные попытки различаются номером попытки `attempts` и токеном `claim_token`, который выдаётся заново при каждой выдаче задания. Выгрузка, которую видит пользователь, хранит ссылку на своё задание, поэтому по экрану и по журналу воркера можно найти одно и то же задание.

Очередь мы сделали в PostgreSQL, а не в RabbitMQ. База у нас уже есть, а брокер стал бы новым сервисом, за которым нужно следить, при нашей ожидаемой нагрузке около пяти запросов в секунду в пиковую минуту. Главное же преимущество в том, что задание создаётся в той же транзакции, что и запись о выгрузке: либо появляются обе, либо ни одной. С брокером для этого понадобился бы Outbox.

## 2. Запуск и обычная обработка

Код лежит в репозитории https://github.com/ScarletFlame611/FamilyQuest в ветке `feature/family-export`, коммит `43ee034` «добавить выгрузку данных семьи через фоновый обработчик». Основные файлы такие:

- `backend/app/modules/jobs/service.py`: постановка, захват, завершение и повтор задания;
- `backend/app/modules/exports/service.py`: запись о выгрузке, сборка архива и сохранение результата;
- `backend/app/worker.py`: сам воркер и команды для проверки;
- `backend/migrations/versions/20261121_0013_family_exports.py`: таблицы `jobs` и `family_exports`;
- `frontend/src/adult/FamilyDataScreen.tsx`: экран «Данные семьи».

Воркер запускается отдельным процессом из того же кода, что и API. В Docker Compose это сервис `worker`, который поднимается вместе с остальными командой `docker compose up -d` и работает командой `python -m app.worker run`. Для проверок мы останавливаем этот сервис и запускаем воркер вручную, чтобы задание не забрал кто-то посторонний:

```bash
docker compose stop worker
docker compose exec backend python -m app.worker enqueue-export mama@familyquest.local
docker compose exec backend python -m app.worker status <job_id>
docker compose exec backend python -m app.worker run --once
```

Первая команда ставит выгрузку для семьи взрослого с этой почтой и печатает идентификаторы выгрузки и задания. Это то же самое, что нажатие кнопки в интерфейсе, и через API это запрос `POST /api/family/exports`. Команда `status` показывает состояние задания, `run --once` обрабатывает одно задание и завершается. В интерфейсе статус и файл видны на экране «Данные семьи», а через API в `GET /api/family/exports` и `GET /api/family/exports/{id}/file`.

Как воркер работает с заданием. Сначала он в короткой отдельной транзакции захватывает одно задание: выбирает строку в статусе `queued` или строку в статусе `running` с истёкшей арендой, пропуская заблокированные другими (`FOR UPDATE SKIP LOCKED`), и одним `UPDATE` ставит ей статус `running`, увеличивает `attempts`, выдаёт новый `claim_token` и срок аренды `lease_until`. Эта транзакция сразу фиксируется, и только после этого воркер начинает собирать архив. Когда архив готов, воркер в одной транзакции отмечает задание выполненным и записывает файл. Отметка выполняется условным `UPDATE ... WHERE id = :id AND claim_token = :token AND status = 'running'`, и вместе с ней увеличивается счётчик `process_count`. Если такая строка не нашлась, значит задание уже выдано другому воркеру: транзакция откатывается целиком, и файл не записывается.

Обычный прогон на демо-семье:

```text
$ python -m app.worker enqueue-export mama@familyquest.local
export=3fd6ec58-efae-46cc-93e2-a54b5f5dbe18 job=e13fd069-7b4c-47b6-95cb-c4d38186b7df status=pending
$ python -m app.worker status e13fd069-7b4c-47b6-95cb-c4d38186b7df
job=e13fd069-... kind=family_export status=queued attempts=0/3 process_count=0 lease_until=None
$ python -m app.worker run --once
10:04:19,121 INFO job=e13fd069-... attempt=1 token=b09270eb claimed kind=family_export lease_until=10:05:19
10:04:19,175 INFO job=e13fd069-... attempt=1 token=b09270eb done
$ python -m app.worker status e13fd069-7b4c-47b6-95cb-c4d38186b7df
job=e13fd069-... kind=family_export status=done attempts=1/3 process_count=1 lease_until=None
```

Задание ждало в статусе `queued`, воркер забрал его с первой попытки, и оно завершилось с `process_count=1`. Готовый архив мы открыли: в нём восемь файлов, а поиск по содержимому не нашёл ни хешей паролей, ни токенов. Тот же путь мы прошли и через интерфейс с воркером из Compose: после нажатия «Подготовить архив» выгрузка показалась как «В очереди», а через секунду сама сменилась на «Готово, 3 КБ, хранится до 28 ноября» с кнопкой «Скачать».

## 3. Проверки

Перед каждой проверкой мы ставили новую выгрузку, чтобы результат первой проверки не влиял на вторую.

| Проверка | Как воспроизвести и какой ID использовали | Что ожидали | Что получили и чем подтверждается |
|---|---|---|---|
| Остановка до записи результата | Задание `53841b63-803f-49ec-87be-a8ec287de680`. Запустили `run --once --crash-after-claim --lease-seconds 10`, воркер забрал задание и завершился с кодом 1. Сразу запустили второй воркер на 5 секунд, затем дождались конца аренды и запустили `run --once --lease-seconds 10` | Пока аренда действует, задание никому не выдаётся. После её окончания то же задание без новой постановки выдаётся снова, с новым токеном и второй попыткой, и завершается один раз | Пока действовала аренда, второй воркер ничего не получил. После неё тот же `job_id` выдан с `attempt=2` и токеном `69ae82fc` вместо `c8977e6c` и завершился. Итог: `status=done attempts=2/3 process_count=1` |
| Попытка старого воркера завершить задание | Задание `a56778a2-777e-4ab8-b8cf-b5a8e16be156`. Воркер A: `run --once --sleep-after-claim 15 --lease-seconds 5`. Через 7 секунд воркер B: `run --once --lease-seconds 5` | B забирает задание после конца аренды A и сохраняет архив. A, проснувшись, получает отказ при записи результата, а архив B остаётся. `process_count` увеличивается один раз | B забрал задание со второй попыткой и завершил его в 10:05:14. A проснулся в 10:05:23 и получил `stale_owner: result discarded`. В базе `status=done`, `attempts=2`, `process_count=1`, у выгрузки `ready_at` совпадает с временем B |

### Проверка 1. Воркер остановился до сохранения результата

Мы ожидали, что упавший воркер оставит задание в статусе `running` с действующей арендой и что никто другой не заберёт его, пока аренда не кончится. После этого задание должно снова попасть к воркеру без новой постановки, под тем же `job_id`, но со второй попыткой и новым токеном, и завершиться один раз.

```text
$ python -m app.worker run --once --crash-after-claim --lease-seconds 10
10:04:34,478 INFO job=53841b63-... attempt=1 token=c8977e6c claimed kind=family_export lease_until=10:04:44
10:04:34,478 WARNING job=53841b63-... attempt=1 token=c8977e6c crash after claim
(код выхода: 1)
$ python -m app.worker status 53841b63-803f-49ec-87be-a8ec287de680
job=53841b63-... status=running attempts=1/3 process_count=0 lease_until=10:04:44
$ python -m app.worker run --once --lease-seconds 10   (сразу, аренда ещё действует)
10:04:38,537 INFO worker started lease=10.0s
(за 5 секунд задание не выдано, воркер остановлен)
$ python -m app.worker run --once --lease-seconds 10   (после истечения аренды)
10:04:51,561 INFO job=53841b63-... attempt=2 token=69ae82fc claimed kind=family_export lease_until=10:05:01
10:04:51,619 INFO job=53841b63-... attempt=2 token=69ae82fc done
$ python -m app.worker status 53841b63-803f-49ec-87be-a8ec287de680
job=53841b63-... status=done attempts=2/3 process_count=1 lease_until=None
```

Так и получилось. К моменту сбоя в базе была сохранена только сама выгрузка и задание в статусе `running` с первой попыткой: архив воркер собрать не успел, а значит, и записывать было нечего. Работу продолжил следующий воркер, который нашёл задание по истёкшей аренде. Пользователь в это время видел «Собираем архив», а после второй попытки получил готовый файл. Флаг `--crash-after-claim` завершает процесс через `os._exit(1)`, без закрытия соединений и без коммитов, как при настоящем падении.

### Проверка 2. Старый воркер пытается завершить задание

Мы ожидали, что воркер A, задержавшийся дольше своей аренды, потеряет задание: его заберёт воркер B, соберёт архив и сохранит его. Когда A проснётся и попытается записать свой архив, условный `UPDATE` не найдёт строку с его токеном, A получит отказ, и его транзакция откатится вместе с файлом.

```text
A: 10:05:08,078 INFO job=a56778a2-... attempt=1 token=1383f626 claimed kind=family_export lease_until=10:05:13
A: 10:05:08,078 INFO job=a56778a2-... attempt=1 token=1383f626 sleeping 15.0s after claim
B: 10:05:14,841 INFO job=a56778a2-... attempt=2 token=c4697d95 claimed kind=family_export lease_until=10:05:19
B: 10:05:14,896 INFO job=a56778a2-... attempt=2 token=c4697d95 done
A: 10:05:23,104 WARNING job=a56778a2-... attempt=1 token=1383f626 stale_owner: result discarded
```

Состояние в базе после обоих воркеров:

```text
 status | attempts | process_count | claim_token |          finished_at
--------+----------+---------------+-------------+-------------------------------
 done   |        2 |             1 |             | 2026-11-21 10:05:14.841843+00

 status | file_size |           ready_at
--------+-----------+-------------------------------
 ready  |      2677 | 2026-11-21 10:05:14.841843+00
```

Результат совпал с ожиданием. Задание выполнено один раз (`process_count=1`), архив и время готовности принадлежат воркеру B, а попытка A отброшена. Защищает это проверка `claim_token` в том же `UPDATE`, которым задание отмечается выполненным. Файл записывается в той же транзакции и только после этой проверки, поэтому опоздавший воркер не может ни перезаписать результат, ни увеличить счётчик.

Обе проверки, а также исчерпание попыток и повтор после ошибки, закреплены автотестами в `backend/tests/test_jobs.py` и `backend/tests/test_family_export.py`. Они входят в общий прогон тестов в GitHub Actions.

## 4. Согласованность данных

Брокера сообщений у нас нет, поэтому двух окон сбоя на границе базы и брокера, ради которых нужен Outbox, в нашей архитектуре не возникает. Задание и есть строка в той же базе, что и бизнес-данные.

Исходные данные для выгрузки, то есть дела, история баллов, награды и остальное, уже сохранены в базе к моменту нажатия кнопки, их выгрузка только читает. Новая запись о выгрузке и задание в очереди создаются одной транзакцией: сервис блокирует строку семьи, проверяет, нет ли уже выгрузки в работе, вставляет задание и запись о выгрузке со ссылкой на него, и только потом транзакция фиксируется. Если транзакция откатится, например из-за обрыва соединения, не останется ни задания, которое собирает несуществующую выгрузку, ни выгрузки, которую никто никогда не соберёт. Пользователь просто нажмёт кнопку ещё раз, а ключ идемпотентности не даст повтору того же нажатия создать вторую выгрузку. Две выгрузки одной семьи в работе одновременно не появятся и при гонке: это запрещает частичный уникальный индекс по семье для выгрузок в статусе `pending`.

Результат задания тоже согласован с очередью: отметка о выполнении и запись архива идут в одной транзакции, поэтому не бывает выполненного задания без файла или файла без выполненного задания.

Outbox понадобится в MVP, когда появится восстановление пароля по почте. Там побочный эффект, отправленное письмо, находится вне нашей базы, и его нельзя откатить вместе с транзакцией. Письмо будет записываться в очередь в той же транзакции, что и токен восстановления, а отправлять его будет этот же воркер. Если почтовый сервис принял письмо, а воркер упал раньше, чем отметил отправку, письмо уйдёт второй раз. Чтобы это было безопасно, у каждого письма будет постоянный идентификатор, по которому почтовый сервис отбрасывает повторы, а ссылка в письме будет одноразовой, так что повторное письмо не даст второго входа.
